### Observed Behavior

Using the file’s exact logic with per-second ticks:

- `11:59:59` → `12:00:00`:
  - stored hour-hand angle: `359.5°` → `360°`
  - delta: `+0.5°`
  - visually correct.
- `12:00:01`:

  - delta: `+360°`

- `12:00:02`:
  - stored angle becomes `1080°`
  - delta: `+360°`
  - visible full spin.
- This repeats every second through `12:59:59`.

  - Stored angle reaches roughly `1,296,030°` by the end of the 12 o’clock hour.
- `13:00:00`:
  - delta returns to `+0.5°`
  - behavior cleanly recovers.
- `13:00:01` onward:
  - delta is `0°` per second, as expected for a minute-only hour-hand model.

Midnight has the same defect:

- `00:00:00` → `00:00:01`:
  - `00:00:00` is visually correct.
  - `00:00:01` onward receives repeated +360° steps.
- Recovery occurs at `01:00:00`.

A fresh page load at exactly `12:00:00` shows a correct first paint, then begins the same spinning behavior from the second tick.

The minute and second hands are unaffected because their raw target angles remain below 360°:

- Minute-hand maximum: approximately `359.9°`.
- Second-hand maximum: `354°` per the Pass 1 simulation.
- No backward rotations occurred in the full-day simulation.
- No wrong modulo-360 position ever occurred in the simulation.

### Expected Behavior

The hour hand should:

- Advance `+0.5°` per minute.
- Remain unchanged per second within a minute, consistent with the existing minute-only hour-hand calculation.
- Creep through the 12 o’clock hour from the 12 position toward the 1 position.
- Wrap from `12:59` to `1:00` with a `+0.5°` step.
- Never perform a full 360° rotation except as a single visually equivalent wrap when crossing 0°, and even that should not appear as repeated full spins.

### Root Cause

`hourDeg` is passed to `applyRotation` unnormalized.

The expression:

```js
now.getHours() % 12 || 12
```

maps both `0` and `12` to `12`. Therefore, for the 12 o’clock hour, the hour base becomes `360°` instead of `0°`.

That makes the raw hour-hand target lie in:

```text
[360°, 390°)
```

The `applyRotation` wrap math assumes the incoming raw target is below 360°. It computes:

```js
target += Math.floor(previous / 360) * 360;
```

then only pushes the target upward while:

```js
target < previous
```

When the raw target is already ≥ 360°, the base-aligned target can land one full turn above `previous`, and the `while` guard accepts it. Nothing subtracts the surplus 360°. The 50 ms CSS transition then animates each accumulated surplus turn.

### Why MEDIUM and Not HIGH

- The defect is reproducible with certainty twice daily: noon and midnight.
- It affects the primary UI element for a full hour each occurrence.
- It is a major visible malfunction.
- However, the static displayed position is always correct modulo 360°.
- The clock never presents an incorrect time.
- No data, security, availability, or other-page impact is identified.
- It self-recovers at `01:00:00` and `13:00:00`.

Therefore it is MEDIUM, not HIGH.

### Required Correction

Normalize the hour angle into `[0°, 360°)` before it reaches `applyRotation`.

Recommended minimal correction at lines 222/227:

```js
const h12 = now.getHours() % 12;
const hourDeg = (h12 / 12) * 360 + (m / 60) * 30;
```

This maps:

- `00:xx` → hour base `0°`
- `12:xx` → hour base `0°`
- `01:xx` → hour base `30°`
- `11:xx` → hour base `330°`

This keeps the existing `applyRotation` monotonic-forward semantics intact and avoids the unforced +360° overshoot.

Alternative acceptable approach from Pass 1: normalize the incoming hour target immediately before accumulation. However, because later passes constrain changes to `applyRotation`, the preferred minimal repair is to normalize the hour angle at the source.

### Preservation Constraints

- Do not alter `applyRotation`’s forward-only accumulation semantics beyond any separate transition suppression required by Pass 2.
- Preserve the 50 ms transition for normal per-second motion.
- Preserve the 1-second boundary alignment of the timer chain.
- Keep the page single-file and dependency-free.

## Finding 5 — `body { overflow: hidden; }` Makes Short-Viewport Content Unreachable

**Finding ID:** Pass 5 / `AC-P5-01`  
**Review Category:** Interfaces, data integrity, integration, configuration, maintainability, and testability — specifically layout/viewport-fit robustness  
**Severity:** LOW  
**Status:** CONFIRMED by runtime verification in headless Chrome/Blink 152.

### Exact Location

File: `C:\Users\default.DESKTOP-M8143Q1\Desktop\Jack Kernel\analog-clock\index_medium.html`

- Line 28:
  ```css
  overflow: hidden;
  ```
  inside the `body` rule, lines 21–33.
- The other `overflow: hidden` at line 65 is on `.clock-face` and is intentional circular clipping.
  - That one is not part of this finding.

### Observed Behavior — Runtime-Verified

Measured fixed content height:

```text

```

Breakdown:

```text
title 36 px
gap 22 px
clock 200 px
gap 22 px
date 19 px
```

At narrow widths where the title `clamp()` shrinks, the height can be approximately:

```text

```

On any viewport shorter than that:

- Example measured headless window:
  - CSS viewport: `784×149`
  - `document.documentElement.scrollHeight`: `299`
  - `innerHeight`: `149`
- User-initiated scrolling does nothing:
  - A dispatched wheel event with `deltaY 800` left `window.scrollY` at `0`.

  - Title: `y = 0..36`
  - Clock: `y = 58..258`
  - Date line: `y = 280..299`

### Expected Behavior

When content exceeds the viewport, the document should scroll, or the layout should shrink to fit.

The date line and full clock face should remain reachable/visible.

### Root Cause

`overflow: hidden` on `body`, with no `html` overflow rule, is propagated to the viewport.

Per CSS Overflow behavior:

- When the root `html` element computes to `visible`, the `body` element’s `overflow` value is applied to the viewport.

This removes scrolling, which is the only mechanism that would make overflowing content reachable.

The layout assumes the viewport is always at least approximately 300 px tall because it uses:

- Fixed 200 px clock.
- Fixed 22 px gaps.
- Text lines.
- Centering via:
  ```css
  min-height: 100vh;
  justify-content: center;
  ```

### Evidence

1. Code:
   - Line 28:
     ```css
     overflow: hidden;
     ```
   - `grep -n "html\s*{"`:
     - No `html` rule exists.
     - Therefore `html` overflow defaults to `visible`.

2. Runtime on the actual page:
   - Viewport: `784×149` CSS px.
   - `docScrollHeight = 299`
   - `innerHeight = 149`
   - Wheel event → `scrollY` remains `0`.
   - Date bounding rect:
     - `top: 280`
     - `bottom: 299`
   - Date is entirely below the 149 px fold.

3. Controls in the same engine and viewport:
   - Page with no overflow rule:
     - Wheel scrolls.
     - `scrollY` moves from `0` to `800`.
   - Page with `html { overflow: hidden; }`:
     - Wheel blocked.
     - `scrollY` remains `0`.
   - This isolates the block to the overflow rule and proves the wheel mechanism itself works.

4. Screenshot captured at `800×300`:
   - Shows the clipped bottom.

5. Caveat:
   - In this headless build, programmatic `window.scrollTo` bypasses the viewport’s `overflow: hidden`.
   - Observed `scrollY` moved from `0` to `150`.
   - This is treated as a headless quirk, not valid page behavior.
   - User-initiated scrolling, specifically wheel, is the valid signal, and it is blocked.
   - In real browsers, the scrollbar simply never appears and wheel/trackpad/keyboard scrolling does nothing.

### Why LOW and Not MEDIUM

- Trigger is an edge case:
  - Viewport inner height below approximately `292–299 px`.
  - Small desktop windows.
  - Split panes.
  - Some low-resolution setups.
- Consequence is limited:
  - The secondary date line becomes silently unreachable.
  - The lower portion of the clock face is clipped.
  - The primary time display remains visible for viewports approximately `160 px` or taller.
- Trivially worked around by resizing the window.
- No data, security, or primary-workflow failure is identified.

### Required Correction

Minimal robust fix:

- Remove:
  ```css
  overflow: hidden;
  ```
  from the `body` rule at line 28.

This allows the document to scroll normally whenever content exceeds the viewport.

Alternative valid approaches, with more work:

- Make the column fit short viewports.
- Use responsive clock size, for example:
  ```css
  width: min(200px, 55vmin);
  height: min(200px, 55vmin);
  ```
- Reduce gaps.
- Add `overflow-y: auto` on `html` or `body`.

The minimal recommended repair is deleting line 28. Nothing else on the page depends on that specific `body` overflow rule.

### Preservation Constraints

  ```css

  ```
  at line 65.
  - It intentionally clips hands to the circular face.
- Keep:
  ```css
  min-height: 100vh;
  justify-content: center;
  ```
  so the layout remains centered on tall viewports.
- Do not alter hand, face, or mark geometry.
